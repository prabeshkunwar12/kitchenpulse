# Database

## Prototype schema

| Table | Columns and relationships |
| --- | --- |
| `items` | Integer primary key `id`, globally unique `name`, free-text `category` and `unit`, integer `quantity` and `minimum`, Boolean `reported`. |
| `movements` | Integer primary key `id`, `item_id` foreign key to `items.id`, integer `delta` and `balance`, Boolean `reversed`, UTC timestamp `created` generated by the application. Many movements can reference one item. |

The startup hook calls `create_all`. The API falls back to a local SQLite file when `DATABASE_URL` is missing. PostgreSQL honors the route's row-locking statements. The SQLite fallback cannot demonstrate equivalent concurrency behavior. Prototype history uses the item's current name, returns the latest 100 rows by ID, and cannot link a reversal to its original row. Threshold and manual-report changes are not stock movements.

## Proposed Phase 1 schema

| Table | Purpose and key rules |
| --- | --- |
| `categories` | Stable category ID and a nonblank unique name. Prevent removal while referenced by active or historical items, or archive the category with a defined lifecycle. |
| `items` | Stable ID, required category foreign key, name, validated unit, current quantity, minimum, manual-report flag and archive state. Constraint-check nonnegative quantities and thresholds. Archive through the API so history remains readable. |
| `movements` | Append-only rows with item ID, movement type, signed delta, resulting balance, historical unit, timestamp and optional `reverses_movement_id` foreign key. Enforce unique reversal link, valid signs/amounts by movement type, no self-link and nonnegative resulting balance. |
| Idempotency records | Durable request key, normalized operation and target/payload fingerprint, and recorded outcome or a durable reference sufficient to replay the original response. Uniqueness applies in the same transaction as each protected operation. |

An opening balance and its opening entry are recorded together. A zero opening balance may have a zero opening movement. Ordinary changes require nonzero deltas. A reversal may target only an eligible original movement for the same item and never produces stock below zero. The service enforces those cross-row rules while holding the item lock. Existing units cannot be reinterpreted after movements exist. Define a deliberate conversion process before enabling unit changes for stocked items.

Start with indexes for category lookups and item history; choose history pagination order deterministically. Prefer a cursor based on a stable sort key and return reversal status from the linked records. Store timestamps in UTC and let the client format them. Set bounded input and database ranges after deciding integer versus decimal quantities.

## Migration and test data

Use Alembic as the schema authority. Apply migrations to a fresh disposable PostgreSQL database first. Inventory in the existing Compose volume must be treated as potentially valuable. Confirm disposition before any schema upgrade against that volume. If it needs preservation, inventory the existing schema, take a backup, rehearse the upgrade against a copy, reconcile item balances and movement counts, and establish how to represent legacy reversal rows without inventing links. Never stamp an unverified database as current.

Seed realistic synthetic inventory with an explicit, repeatable command. Use stable seed identities and avoid overwriting quantities after a demo item has been used. Exercise PostgreSQL locks, uniqueness and rollback using isolated test data. Keep the sequence, balance and signed movement total consistent per item.
